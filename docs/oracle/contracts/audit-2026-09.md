# Supabase Schema & Data-Access Audit — September 2026

**Scope:** Current Supabase schema (generated types in `src/types/supabase.ts` + migrations in `supabase/migrations/`) and data-access code in `src/lib/`, audited against `docs/oracle/decisions.md`.

**Method:** Every D-series decision is marked **Matches / Mismatch / Can't tell**. Claims about existing behaviour are tagged `[Confirmed: path]`.

---

## 1. Data model

### D-001 — Three core tables: `card_definitions`, `physical_copies`, `deck_cards`. Proxies are `physical_copies` rows with `is_proxy = true`.

**Status: Mismatch**

- The locked decision names are not the current schema names. Migrations renamed:
  - `card_definitions` → `cards` → `user_cards` [Confirmed: `supabase/migrations/20260730032938_rename_card_tables.sql` lines 2, 22-23; `supabase/migrations/20260730044951_rename_tables_prefix_convention.sql` lines 6, 25-26]
  - `physical_copies` → `copies` → `collection` → `user_copies` [Confirmed: `supabase/migrations/20260730032938_rename_card_tables.sql` line 4; `supabase/migrations/20260730033009_merge_copies_into_collection.sql` line 96; `supabase/migrations/20260730044951_rename_tables_prefix_convention.sql` lines 7-8, 38-44]
  - `deck_cards` retained its name [Confirmed: `supabase/reconciliation/pre-ledger/outer-migrations/20260702112616_001_initial_schema_tier5a.sql` line 1]
- Proxy semantics do match the decision: `user_copies.is_proxy` is a boolean and proxies are rows in the same table [Confirmed: `src/types/supabase.ts` lines 1991, 2010, 2029; `src/lib/card-identity-store.ts` lines 36-50].

The conceptual model is intact, but the locked table names are not what is deployed.

### D-002 — Deck lifecycle has exactly three states: Brew / Boxed / Archived.

**Status: Mismatch**

- The deployed model does not use Brew / Boxed / Archived. Application types still define a legacy enum of `'brewing' | 'in_rotation' | 'graveyard'` [Confirmed: `src/lib/deck-status.ts` lines 15-21; `src/lib/brew-v2-types.ts` line 9].
- The `decks` table has both a `status` string column and an `is_active` boolean [Confirmed: `src/types/supabase.ts` lines 820-922].
- A migration explicitly states it "Replaces the brewing/in_rotation/graveyard status lifecycle with a simple boolean toggle" [Confirmed: `supabase/migrations/20260804131924_add_is_active_to_decks.sql` lines 2-6].

The locked three-state lifecycle is not implemented.

---

### D-003 — `scryfall_id` (printing) and `oracle_id` (canonical card) are never interchangeable. Resolution functions are discrete and unit-tested.

**Status: Matches (with gaps)**

- Reference table stores printings correctly: `ref_printings.scryfall_id` is the printing key and `ref_printings.oracle_id` is the canonical key [Confirmed: `supabase/reconciliation/pre-ledger/outer-migrations/20260726160000_scryfall_printings.sql` lines 11, 14].
- `user_cards.oracle_id` holds the canonical card identity [Confirmed: `src/types/supabase.ts` lines 1953-1981].
- `user_copies.printing_id` holds the physical-copy printing (Scryfall ID) [Confirmed: `src/types/supabase.ts` lines 1983-2085].
- `deck_cards.scryfall_id` holds the slot's wanted printing [Confirmed: `src/types/supabase.ts` lines 304-386].
- Identity validation is enforced at the DB boundary: the `validate_deck_card_copy_identity` trigger resolves a slot's `scryfall_id` to its `oracle_id` and rejects assignments where the copy's canonical identity differs [Confirmed: `supabase/migrations/20260912170000_atomic_collection_personal_scope.sql` lines 49-64].
- Resolution is performed by discrete, tested functions rather than inline logic: `identity-resolver.ts`, `card-definition-resolver.ts`, `commander-resolver.ts`, `warm-start-resolve.ts` [Confirmed: `src/lib/identity-resolver.ts`; `src/lib/card-definition-resolver.ts`; `src/lib/card-definition-resolver.test.ts`].

Gaps observed (not direct violations of the decision, but architectural drift):

- Identifier columns in user tables lack comments saying whether they hold a `scryfall_id` or `oracle_id` [Confirmed: `supabase/migrations/20260730033009_merge_copies_into_collection.sql`, `supabase/migrations/20260730044951_rename_tables_prefix_convention.sql` — no `COMMENT ON COLUMN` statements for `user_cards.oracle_id`, `user_copies.printing_id`, or `deck_cards.scryfall_id`].
- Type impedance: `ref_printings` uses `UUID` for both identifiers, but `user_cards.oracle_id`, `user_copies.printing_id`, and `deck_cards.scryfall_id` are `TEXT` [Confirmed: `src/types/supabase.ts`].
- Naming inconsistency for the same concept: a printing is `scryfall_id` in `deck_cards` but `printing_id` in `user_copies` [Confirmed: `src/types/supabase.ts`].

### D-004 — Finish (normal / foil / etched) is an independent attribute on the physical copy.

**Status: Mismatch**

- `user_copies.finish` is an independent column, separate from printing ID, satisfying the structural requirement [Confirmed: `src/types/supabase.ts` lines 1989, 2008, 2027; `src/lib/card-identity-store.ts` lines 36-50].
- However, the canonical values used in code and stored in the DB are `'nonfoil' | 'foil' | 'etched'`, not the decision's `'normal' | 'foil' | 'etched'` [Confirmed: `src/lib/card-identity-store.ts` line 40; `src/lib/identity-resolver.ts` lines 164-184].
- There is no database `CHECK` constraint on `finish`, so any string can be inserted [Confirmed: `src/types/supabase.ts` — `finish: string | null`].

The attribute is independent, but the value vocabulary and lack of a constraint do not match the decision.

---

### D-005 — Maybeboard is modelled as a separate `deck_cards` relation.

**Status: Mismatch**

- There is no `is_maybeboard`/`board` column and no separate maybeboard table [Confirmed: `src/types/supabase.ts` `deck_cards` schema lines 304-386].
- Maybeboard and sideboard are distinguished by category strings (`'Maybeboard'`, `'Sideboard'`) inside the JSON `deck_cards.categories` column [Confirmed: `src/lib/deck-versions.ts` lines 175-197; `src/lib/deck-normalizer.ts` line 81; `src/app/api/decks/[id]/card-statuses/route.ts` lines 75-78].

The maybeboard is not modelled as a separate relation; it is a category convention.

### D-006 — Clean slate beats complex migration: prefer flush-and-rebuild over a convoluted migration (owner approval required).

**Status: Can't tell**

- The migration history contains complex chained renames and merges rather than a clean rebuild (e.g., `rename_card_tables.sql`, `merge_copies_into_collection.sql`, `rename_tables_prefix_convention.sql`) [Confirmed: `supabase/migrations/20260730032938_rename_card_tables.sql`; `supabase/migrations/20260730033009_merge_copies_into_collection.sql`; `supabase/migrations/20260730044951_rename_tables_prefix_convention.sql`].
- No owner-approval citation is visible in the migration headers or in the audited code.
- Whether a clean slate was considered and rejected is outside the artifacts reviewed.

## 2. Allocation

### D-007 — The destructive clear-and-recompute Allocation Resolver is retired as a write path. Its compute layer is reused as a suggestion engine that proposes allocations without writing them.

**Status: Mismatch**

- The suggestion engine is read-only and non-destructive: `allocation-candidates.ts` explicitly states it is "READ-ONLY — no writes, no clearing" [Confirmed: `src/lib/allocation-candidates.ts` lines 1-10, 62-72].
- Import reconciliation uses provisional `import_sleeve_claims` rows instead of writing final allocations [Confirmed: `supabase/migrations/20260917003132_import_sleeve_claims_table.sql` lines 1-21].
- **However**, the destructive RPC `allocation_clear_active_decks(p_user_id UUID)` still exists in the generated schema [Confirmed: `src/types/supabase.ts` lines 2198-2201] and was defined to clear `physical_copy_id`/`ownership_status` on active-deck slots [Confirmed: `supabase/reconciliation/pre-ledger/outer-migrations/011_allocation_clear_rpc.sql` lines 11-35]. No later audited migration drops it.

The compute layer has been retired in practice, but the destructive write path is still present in the schema.

## 3. Brew Canvas

### D-008 — Free-drag with snap-to-grid at launch.

**Status: Matches (schema supports)**

- Canvas positions are persisted in `brew_sessions.skeleton_json` / `assessment_cache_json` and in the `DeckState.canvasPositions` record [Confirmed: `src/types/supabase.ts` `brew_sessions` / `oracle_sessions` sections; `src/lib/brew-v2-types.ts` lines 170-183; `src/lib/brew-autosave-serializers.ts`].
- Snap-to-grid behaviour is UI-level; the schema provides the storage needed.

---

### D-009 — Drag-to-assign is the single placement mechanic. Every placement carries a `source` parameter (e.g. `manual`, `ai`) so undo, validation and audit logging are shared across manual and AI placement.

**Status: Mismatch**

- `deck_cards` has no `source` column or audit column for placement origin [Confirmed: `src/types/supabase.ts` lines 304-386].
- The assignment API body accepts `deckCardsId`, `physicalCopyId`, and `tier` — no `source` parameter [Confirmed: `src/app/api/allocation/assign/route.ts` lines 21-25, 46].
- Proxy creation sets `source_tag = 'manual'`, but that is on the `user_copies` import-provenance column, not on the placement itself [Confirmed: `src/app/api/allocation/add-proxy/route.ts` line 13; `src/app/api/collection/instances/add-proxy/route.ts` line 54].
- `user_copies.source_tag` is used for import source tracking, not for distinguishing manual vs AI placement [Confirmed: `src/lib/import-engine-v2.ts`].

The `source` placement parameter required by the decision is not implemented.

## 5. AI features

### D-016 — Structured data from LLMs comes via tool use or a JSON sidecar block. No regex parsing of prose.

**Status: Mismatch**

- Anthropic path uses native `tool_use` blocks and parses JSON input [Confirmed: `src/lib/adapters/anthropic-adapter.ts` lines 126-149].
- Gemini path uses native function calling [Confirmed: `src/lib/adapters/gemini-adapter.ts` lines 196-250].
- **DeepSeek path parses DSML/XML tool-call markup out of model-generated prose with multiple regexes** [Confirmed: `src/lib/adapters/deepseek-adapter.ts` lines 459-530, especially `parseDsmlToolCalls` and `stripResidualDsml`].

The DeepSeek adapter violates the decision's prohibition on regex parsing of LLM prose for structured data.
