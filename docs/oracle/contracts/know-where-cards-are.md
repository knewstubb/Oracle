## 1. What the owner gets (plain words)

He picks cards to move. Oracle shows one checklist grouped by where he walks. For each card he ticks **Found** (the card leaves its deck in Oracle at once and sits in **In your hand**) and then **Placed** (it goes into a deck or a box). If he cannot find a card he taps **Can't find it**: the card goes to **Missing**, the deck keeps the card's slot and shows short by one, and Oracle suggests where to look next. If he stops part-way, ticked moves stay done and the rest stay where Oracle last had them.

Three system locations, always present: **In your hand**, **Missing**, **Unsorted** (existing name, used for new imports). The owner cannot delete them.

**Two ways to move a card (2026-11-13).** (1) **Move here** (primary): in a deck, a card whose copy sits in another deck gets a button that moves that copy to this deck at once, in one click, with a short Undo. It assumes the physical card is being moved straight away: no In your hand step, no checklist, no reminder. (2) **The Picklist** (optional, for walking the shelves): Found it, Placed it, In your hand, Can't find it, as described above. "Add to Picklist" (formerly "Add to move checklist") stays as a small secondary option next to Move here.

**One concept: the Picklist (2026-11-13).** There is no separate "checklist" and "Sleeve List" any more. Each deck's Picklist tab lists everything needed to complete that deck in three groups: **Available** (owned, free in a box or Unsorted: pick and place), **Needs moving** (owned, but the copy is in another deck: Move here, or Found it / Placed it with In your hand), **Unowned** (not owned: buy ideas, prices and the wishlist side). The all-decks view is the same list combined across decks in walking order. Found it / Placed it ticks are saved once and show in both views. Details in section 4b.

So: Unsorted and Missing fit; In your hand needs a schema change. The smallest design is **two columns on `user_copies`, one table, two guard triggers.** No existing row changes.

Why a column and not a location row for In your hand: it needs no per-user seeding (a public version would otherwise need a signup hook), no lookups to find the row, and it cannot be renamed or deleted. The app still shows it as a location with a count. Why Missing stays a flag: the existing SQL functions already test `missing = false` and need no rewrite to keep refusing those copies.

Rejected alternatives: (a) derived "in hand" from "has an open checklist item": breaks if the item is cancelled and cannot be queried cheaply from the many existing "free copy" readers; the owner already rejected "derived state" (brief 17.4). (b) New `user_locations` rows for In hand and Missing: dual truth with the existing `missing` flag, plus seeding for every new user.

## 3. Schema (DRAFT files, not applied)

### 3.1 `supabase/migrations/20261113100000_copy_in_hand_and_missing_since.sql`
- `user_copies.in_hand boolean NOT NULL DEFAULT false`; `user_copies.missing_since timestamptz NULL`.
- Primary key `user_copies.id` (unchanged). No new foreign keys. Not an identifier column (D-003 not touched).
- `CHECK (NOT (in_hand AND missing))`.
- Trigger `user_copies_keep_one_place` (BEFORE): setting a storage location or `missing` clears `in_hand`; `missing_since` follows `missing`. Effect: any older path that puts an in-hand copy in storage (for example `unassign_copy_to_storage`) simply lands it in Unsorted, valid.
- Trigger `deck_cards_copy_must_be_available` (BEFORE, only when `copy_id` is set to a new non-null value): raises `copy_in_hand` / `copy_missing`. Existing rows and every clearing path are untouched. This is the safety net for older SQL that has not learned about `in_hand` (section 6).
- Partial indexes on `(user_id) WHERE in_hand` and `WHERE missing` for the two lists.
- Existing-data impact: live has 4,259 copies, 0 missing, 0 location-less outside a deck, so nothing changes. Metadata-only column add on Postgres 17. Reversible (rollback block at the bottom of the file). Applying it alone changes nothing the owner sees.

### 3.2 `supabase/migrations/20261113100100_move_items.sql`
Table `move_items` (PK `id` bigint identity). Columns: `user_id`, `list_id` (groups one checklist), `copy_id` (a `user_copies.id`, FK ON DELETE SET NULL), `card_name` (display snapshot), `from_deck_id` / `from_deck_card_id` / `from_location_id`, `to_deck_id` / `to_deck_card_id` / `to_location_id`, `state` in `to_find | found | placed | missing | cancelled`, `looked_in jsonb`, `source` in `manual | import | ai` (D-009), timestamps. All foreign keys are ON DELETE SET NULL so deleting a deck, box or copy never deletes history. Constraints: at most one "from", exactly one "to". Unique partial index: a copy is on at most one open item (`to_find`/`found`). Indexes: `(user_id, list_id)`, `(user_id, state) WHERE open`. RLS on, select-own policy; writes only through the service-role RPCs below (same pattern as `chat_card_proposals`). Reversible by dropping the table (it holds only checklist rows). Additive only.

## 4. Behaviours (the rules the build must satisfy)

B1. **Found.** Ticking Found on an item in `to_find`: if the copy sits in a deck slot, that slot's `copy_id` is cleared at once (the slot stays on the list as a planned slot, so the deck shows **short by one** and the slot reads Unsleeved, D-025/D-033); if it sits in a box, `location_id` is cleared. Then `in_hand = true`. The card now appears under In your hand. Source deck and box counts change immediately.
B2. **Placed.** Ticking Placed on a `found` item puts the copy into the target: a deck target fills a planned slot (the item's own slot if still empty, otherwise another empty slot for the same card in that deck); a box target sets `location_id`. `in_hand` becomes false first so the guard trigger passes. "Put it back anywhere" is allowed: Placed with an overriding target (any deck with an empty slot, or any box including Unsorted).
B3. **Can't find it.** Allowed on `to_find` (never found) or `found` (dropped on the way). The copy is flagged Missing (`missing = true`, `in_hand = false`, `location_id = null`, slot cleared if it was in a deck). The item state is `missing`. The response lists every deck now short (each keeps its planned slot) with a suggestion of `proxy`, `spare_copy` or `none`, and a ranked **look next** list: (1) other decks that list this card by name (it may be in their sleeves), (2) Unsorted, (3) other boxes by name, excluding anything already in `looked_in`. [Approximate: the ranking is a sensible default, not an owner decision.] Each "I checked here, not there" appends to `looked_in` and shrinks the list. The flag stays until **Turned up**.
B4. **Turned up.** From the Missing list or the item: the copy leaves Missing and goes to a chosen box, a deck with an empty slot, or In your hand. It never returns to a deck slot by itself.
B5. **Missing cards cannot be allocated** by any route (suggestions, auto-assign, import claims, chat, manual assign) and are **excluded from spare** and from owned-for-buying maths. In-hand cards are treated the same until placed (they are not spare either).
B6. **A deck that loses a card to Missing keeps the slot**, shows short by one (D-002: the list is still 100, so the deck reads Assembling, not Draft), and Oracle suggests a proxy (existing Proxy action, D-026, one click, never automatic) or a spare copy if one exists.
B7. **Part-way is safe.** Every tick is its own saved step. Closing the app leaves ticked moves done and unticked cards where Oracle last had them. Reopening the checklist (`GET /api/moves/open`) resumes it. Cards left In your hand stay there and are always listed; nothing returns them automatically.
B8. **Two ticks per move, nothing else needed.** There is no "start" or "finish" step.
B9. **Proxies** behave like any copy. A move may carry a `swapHint` ("a real copy is in Prosper; Korvold would use it better") from the existing Phase 5 ranking when it exists; until then it is null. Hints are shown, never applied.
B10. **Not generic basics.** Generic basic lands have no copies (D-032), so they never appear on a checklist.

## 4a. Move here: direct move between decks (2026-11-13, owner decision)

**Existing move code found (reuse, do not rebuild).** [Confirmed: `supabase/migrations/20260925220000_placement_source.sql`, `src/app/api/allocation/reassign-to-deck/route.ts`, `src/app/api/allocation/claim-from-deck/route.ts`, `src/app/api/allocation/undo/route.ts`, `src/types/placement-source.ts`]
- `reassign_to_deck(copy, target deck, card name, user, source)`: one transaction under the per-copy lock; finds the copy's current slot, finds an **empty slot for that card name** in the target deck, clears the old slot, fills the new one (`ownership_status` follows proxy/original, `placement_source` recorded), returns both slot ids. Refuses missing copies (`copy_missing`), copies not in a deck (`copy_not_assigned`), and no empty slot (`no_open_slot`). Route `POST /api/allocation/reassign-to-deck` wraps it.
- `undo_copy_move(current slot, copy, restore slot, user)`: exact undo; refuses with `slot_claimed_elsewhere` if the old slot was filled since and `current_assignment_mismatch` if the copy moved again. Route `POST /api/allocation/undo`.
- `claim-from-deck` (force-claim into a chosen slot) exists for the older "Tier 4" modal and is not used by Move here.
- Gaps found: (a) `reassign_to_deck` does **not** check that the target is a different deck from the copy's current deck, so a stale screen or double click on a deck that wants two copies could shuffle a copy between two slots of the same deck; (b) it does not look at the source deck's `allocate` flag (fine for an explicit physical move); (c) it returns slot ids only, not deck names or the short-by-one fact the toast needs.

**Behaviour.**
- M1. Where it shows: on a deck row (planned slot, no copy) when the owner has a **real or proxy copy sitting in another deck**. Primary button **Move here**. If several copies sit in several decks the owner picks which copy (the call always names one copy; the server never guesses). Default pick, when a default is shown: the same ranking the Allocation candidates already use (requested printing first, then alternates; real before proxy) [Confirmed: `src/lib/allocation-candidates.ts` `classifyTier`/`scoreCandidate`], with the source deck named on the button or row.
- M2. One click = one atomic move: the copy leaves the source deck's slot and fills this deck's planned slot. The source deck **keeps its slot and now shows short by one** (D-025). The copy never passes through In your hand, creates **no `move_items` row and no reminder** (owner: clicking means the card is being moved now).
- M3. Short Undo toast: "Moved from <deck>. Undo." naming the source deck and saying it is now short by one (brief section 13: never leave another deck short without saying so). Undo = `undo_copy_move` with the source slot as the restore target. Undo is by data check, not a timer: it works while the source slot is still empty and the copy still sits in the target slot, otherwise it is refused with a plain message and nothing is overwritten. The toast timer is a UI matter (Designer).
- M4. **No empty slot for the card in this deck.** Move here is not offered; the row offers **Add to deck** (planned slot only, existing behaviour). Right after Add, the same row offers **Move here** (two separate steps, each atomic and each undoable; never a silent combined add-and-move). [Recommendation; owner can ask for a one-click combined action later.]
- M5. **Source deck is built, active or Playable.** Allowed, instant. The source deck drops from Playable to Assembling (D-002) because its slot is now empty; the toast says so. Whether to ask first for a Playable source is owner question Q6.
- M6. **Copy is on an open checklist item** (`to_find` or `found`, once `move_items` exists): Move here refuses with `copy_on_open_checklist` and the message points to finishing or cancelling that checklist step. A copy In your hand is never a Move here candidate (it has no deck); it uses Placed it.
- M7. **Missing or already in this deck:** refused (`copy_missing`, `already_in_this_deck`). A stale screen (copy moved since the page loaded) gets `source_changed`, not a wrong move.
- M8. **Multiple clicks and two tabs.** The check "copy is still in the deck the screen showed" plus the per-copy lock make a second click a no-op error, not a second move.
- M9. Generic basic lands have no copies (D-032) and never show Move here.
- M10. Not for AI: the chat does not move physical cards (D-034 would then require undo; out of scope).

**RPC (new, thin, no schema change).** `move_copy_to_deck(p_copy_id integer, p_target_deck_id integer, p_card_name text, p_expected_source_deck_id integer, p_user_id uuid)`: in one transaction, lock the copy, verify the copy's current deck equals `p_expected_source_deck_id` and differs from the target, verify no open checklist item (when the table exists), then call `reassign_to_deck` (same transaction), and return `{ success, copyId, sourceDeckId, sourceDeckName, sourceDeckCardId, targetDeckCardId, sourceDeckNowShort, sourceDeckStatusAfter }`. Service role only, same grant pattern as the other move RPCs. The Developer writes the body in its own migration (no table or column change, so it needs no stored-data approval beyond the usual migration review).
**Route.** `POST /api/decks/[id]/move-here` body `{ copyId, cardName, expectedSourceDeckId }` returning `MoveHereResponse` (types file). Undo uses the existing `POST /api/allocation/undo` with `{ deckCardsId: targetDeckCardId, physicalCopyId: copyId, restoreTo: { deckCardsId: sourceDeckCardId } }`.

## 4b. The Picklist: one concept, per deck and all decks (2026-11-13, owner decision)

**What it is.** The existing per-deck pick list screen (`PicklistV2`, tab "Sleeve List") and the new checklist become one thing. Per deck, the Picklist lists everything needed to complete that deck, in three groups. The all-decks Picklist is the same rows combined for the chosen decks, in walking order. Nothing new is stored for the list itself: the list is computed from the deck's planned slots and the owner's copies (as today), and the only saved things are the Found it / Placed it ticks (`move_items`, section 3.2), which are shared by both views.

**Reuse of the existing screen and API (reuse, do not rebuild).** [Confirmed: `src/components/PicklistV2.tsx`, `src/app/api/decks/[id]/picklist/route.ts`, `src/lib/allocation-candidates.ts`, `src/lib/card-status.ts`]
- Route `GET /api/decks/[id]/picklist` already returns, for the deck, every non-generic slot with `lifecycle`, `copyId`, `isResolved` and, for each planned slot, ranked `candidates` (each says whether the copy is free or sits in another deck, with the box or deck name and deck status), plus `progress {resolved, total}`. Generic basics are excluded (D-032).
- Screen `PicklistV2({ deckId })` groups those candidates on the client with a function `categorizeCards` into: Available groups by box, Claimed groups by source deck, and Unowned. These **are** the three new groups under new names: Available stays Available; Claimed becomes **Needs moving**; Unowned stays **Unowned**.
- **Preserved:** the route's current fields and meaning (additive changes only); the `PicklistV2` export and its `deckId` prop; `PicklistProgress` (also used by the Cards tab, deck skeleton, deck page and reconciliation summary; its numbers do not change); the candidate ranking; the direct one-click place of a free copy (today's "Sleeve" button, now **Placed it**); Proxy actions; the per-row loading, error and D-030 stale-data behaviour.
- **Replaced:** the "Sleeve from Active deck?" force-claim confirm and its `claim-from-deck` call (the old Tier 4 path) become **Move here** (section 4a) for copies in another deck, plus the shelf flow below. The route `claim-from-deck` is left in place until close-out checks that nothing else calls it [Approximate: grep before deleting]. Button and tab words change (section 13).
- **Added:** the shared grouping function moves out of the component into a small tested library file so the route, the screen and the all-decks view use one definition; ticks and In your hand state on rows; the all-decks route.

**How the three groups are derived from the existing availability logic.** Per planned slot (`copy_id` null, not generic), using the same candidate list as today, after the S0 supply rule (section 6) so Missing and In-hand copies are not supply:
1. **Available** = at least one candidate copy that is free (no deck row, not Missing, not In hand). Shown grouped by the box it is in (Unsorted included), exactly as today. Actions: **Placed it** (one click, today's direct assign, no hand step) or the two-tick **Found it** then **Placed it** for someone walking the boxes. A free copy always wins over a copy in another deck, as in today's `categorizeCards` (free first).
2. **Needs moving** = no free copy, but at least one owned copy sits in another deck (the current "claimed" case), **or** an owned copy is In your hand or Missing (waiting on the checklist). Grouped by source deck. Actions: **Move here** (section 4a; several copies means the owner picks; refused for a copy waiting on a checklist step), or the shelf flow **Found it** then **Placed it**, which passes through In your hand. A copy already In your hand shows **Placed it** only; a Missing copy shows its Missing line and Turned up, never Move here.
3. **Unowned** = no copy owned at all (the current candidates-empty or tier 5 case). Shows what the screen shows today (name, available buy ideas and prices from the existing buy logic [Confirmed: `src/lib/deck-health-buy.ts`], "est." rule unchanged) and, later, wishlist. A failed lookup is "could not check", never Unowned (D-030).
Rule: each slot is in exactly one group; a card needed twice appears per slot; rows for slots already holding a copy are not listed (the list is what is still needed).

**All-decks view (the combined Picklist).** `GET /api/picklist?deckIds=1,2,3` (omitted = all decks that have planned slots): the same rows merged, grouped as a walk: first **take from boxes** (by box, Unsorted first or last as the Designer decides), then **take from decks** (by source deck), then **place in** each target deck, then Unowned at the end (not a stop). This is the existing `Checklist` / `ChecklistGroup` shape in the types file with a `kind` per row. Ticks are `move_items` rows keyed by copy and target, so a tick made in a deck's Picklist shows on the all-decks view and the other way round (the same row, never a copy of it). Creating a tick for a row that has no item yet creates the item and ticks it in one transaction (`POST /api/picklist/found` and `.../placed` take `{ copyId, to }` and call the same RPCs as section 5).

**Wishlist and Unowned (LATER slice; no design here).** [Confirmed: `src/app/api/onboarding/reconciliation/instance/wishlist/route.ts`, `src/components/reconciliation/WishlistCheckbox.tsx`, `src/components/reconciliation/ConflictCard.tsx`, `src/lib/import-reconciliation.ts` `setClaimWishlist`, RPC `set_import_claim_wishlist`, `src/types/supabase.ts`] Today the only wishlist is a yes/no flag `wishlist` (default true) on each import reconciliation claim row (table `import_sleeve_claims`), set from the Unowned tab of the import reconciliation screen. It is deliberately inert (changes no count or deck row) and exists only for a card that came in through an import conflict and is unowned. It is not a list of cards the owner wants to buy, and a card that is unowned in a deck but never went through an import has no wishlist row. So **the Unowned group can show buy ideas and prices from existing logic in the first slices with no new storage**, but a real "wishlist side" (add, see, remove wishlist cards from the Picklist) **needs new storage or a decision to reuse the claim flag**, which is a LATER slice and needs owner approval. Question Q8 asks whether a separate wishlist feature is wanted; this contract does not design a shopping feature, and no migration is drafted for it.

**Risk to existing picklists.** Nothing is saved today for pick lists (computed on each view), so there is no stored data to migrate or lose. Risks: (1) the screen is large (about 770 lines) and the route also feeds the Cards tab, the deck page and chat facts [Confirmed: grep of `PicklistV2|/picklist` in `src/`]; mitigation: additive route fields, extract the grouping with unit tests that reproduce today's grouping on fixed inputs before any rename; (2) the old force-claim confirm disappears, so a user used to it sees Move here instead; (3) copies Missing or In hand must not appear as Available (fixed by S0, the same prerequisite as everything else); (4) the tab keeps its query-string value `picklist` so old links still open it (the label changes, the address does not).

## 4c. Import destination: one place for the whole import (2026-11-13, owner decision)

**What the owner gets.** When importing cards into the collection, one extra choice: **where do these cards go?** One answer for the entire import, never per card. Default **Unsorted** (exactly today's behaviour). The dropdown also lists every storage box or binder (for example a "Valuable binder") and every deck. Examples: cards bought for Korvold go straight into Korvold; the expensive pulls go straight to the Valuable binder.

**What exists today.** [Confirmed: `src/lib/import-copies.ts` `toCollectionRpcRow`, `src/lib/manabox-collection-import.ts`, `src/lib/import-engine-v2.ts`, `supabase/migrations/20260912163000_atomic_collection_insert_ids.sql`]
- Every imported copy is built with `location_id: null`; the insert RPC `insert_user_copies` swaps a null for the user's default storage location (Unsorted) inside its transaction, **but it already accepts a real `location_id` per row** and refuses one that is not the user's (`storage_location_not_found`). It returns the new copy ids (`inserted_ids`). So a box or binder destination needs **no database change**.
- A deck destination has no existing import path. Add-only imports never touch decks (D-020: import runs no allocation pass). The placing code does exist: `assign_free_copy` (fill the deck's empty slot for a card name; sets `ownership_status`, `placement_source`, clears `location_id`), `POST /api/decks/[id]/cards` (add a slot by card name, no copy), and the identity guard trigger on `deck_cards` (a copy must match the slot's card).
- Scope: the **add-only collection import** (the ManaBox collection dialog and its `?mode=manabox` / JSON route, including the streamed variant). **Not in scope:** replace and sync modes (they remove copies, so one destination makes no sense), deck import (it creates its own deck), the legacy add mode and onboarding imports (they stay Unsorted; the picker is not shown). [Approximate: the Developer confirms by grep that no other caller of the collection insert needs the picker.]

**Where the picker sits in the flow.** On the **review step**, after the file is read and matched and before the owner presses Import, directly under the existing "Importing as: Non-foil · Near Mint · English  Change" bar. It follows the same pattern: a line "Putting them in: **Unsorted**  Change" that opens a dropdown. The Import button reads "Import 40 cards" for Unsorted and "Import 40 cards to Korvold" otherwise. The choice is **not remembered** between imports (recommendation: always starts at Unsorted, so a forgotten setting never sends a later import to a deck). The "unsaved changes" warning that already guards the dialog counts a changed destination. Designer owns the look (Gate 3 spec first).
- Dropdown content, in order: **Unsorted** (first, default); **Boxes and binders** (every storage location the user owns, in the existing sort order); **Decks** (every deck, each with a short hint such as "9 empty slots"). Chosen deck options show the deck's readiness word.
- With a **deck** chosen, the review step may show a one-line **forecast** from a dry run: "About 12 will fill empty slots, 3 are not on the list yet and will be added, 2 will go to Unsorted." It is a forecast; the result screen states the real numbers.

**What counts as a valid destination.**
- Valid: Unsorted (the default storage location); any other `user_locations` row of type `storage` owned by the user; any deck owned by the user.
- **Not offered and refused by the server:** **Missing** and **In your hand**. They are not location rows (they are the `missing` and `in_hand` markers on a copy, section 2), so they can never be a destination, and an import never creates a copy in either state. The `user_locations` rows of type `deck` (one auto-created per deck, unused for copies) are also hidden; a deck is chosen from the decks list, never from a location row. A destination of another user's location or deck is refused (not found, nothing revealed).
- Anything else in the request (an unknown kind, both a location and a deck, a deck-type location id) is refused with 400 before anything is written.

**Data and API shape (additive; omitting it gives today's behaviour exactly).**
- Request: an optional field `destination` on the collection import body (JSON body, or a JSON form field when multipart), beside `defaults` and `copyEdits`. Shape: `{ kind: 'unsorted' } | { kind: 'storage'; locationId: number } | { kind: 'deck'; deckId: number }`. Absent equals `{ kind: 'unsorted' }`. The user id still comes only from the session.
- `GET /api/import/destinations` (new, read only): `{ unsorted: { locationId }, storage: [{ locationId, name, copyCount }], decks: [{ deckId, name, format, emptySlots, status }] }`. Failure reads as "could not load destinations" with Unsorted still usable (D-030: never an empty list that looks final).
- `POST /api/import/destination-preview` (new, read only, optional): same body as the import minus the file work; returns the deck forecast counts from the same planner the write uses (below). Cut from the first slice if time is short; the result screen is the required part.
- Response: the existing collection import summary gains an optional `placement` field (types file). Existing fields are unchanged.
- Types: `ImportDestination`, `ImportPlacementResult`, `DestinationsResponse` in the types file.

**Rules for a storage destination (box or binder).** Every imported copy gets that `location_id`. Written through the existing `insert_user_copies` RPC unchanged: in the same transaction, all or nothing. Result: "40 added to Valuable binder". Nothing else changes.

**Rules for a deck destination** (owner agreed; the rest are the Architect's rules, recommended, see questions Q9 to Q12). Copies are created in the collection as always, then each is placed **in file order**, by this ladder, first match wins:
1. **Fills a planned slot.** The deck lists this card on the main list with an empty slot (`copy_id` null). Prefer a slot asking for the same printing and finish, then any empty slot for the same card (an alternate printing is an alternate, as everywhere else; ties go to the lowest slot id). The copy is assigned to the slot: `ownership_status` follows proxy or original, `placement_source = 'import'` (allowed value, D-009), `location_id` cleared (a copy in a deck has no location).
2. **Added as a new slot.** The deck does not list this card on the main list at all (and it is not in the deck's Maybeboard), and the format's limit is not reached (singleton formats: 1; formats with a copy limit: that limit). A new main-list slot is created (printing, set, finish from the imported copy; default category by the same rule as adding a card by name) and the copy is assigned to it. Basic lands never take this step (rule 4).
3. **Sent to Unsorted.** Everything else stays where an ordinary import puts it, with a stated reason: **duplicate** (the deck already has every allowed copy of this card filled, for example a second Sol Ring in a singleton deck, or a second copy of the same card within this same import), **in the Maybeboard** (the card is only on the deck's Maybeboard; the owner promotes it from the deck page), **basic land** (basic lands and Wastes are generic in decks, D-032; they fill an empty tracked basic slot if the deck has one, otherwise go to Unsorted), or **could not place** (the slot was taken or the card did not match the slot at the moment of writing; see atomicity).
Nothing is dropped: **filled + added as new + sent to Unsorted = copies added**, always, and the result screen shows all three numbers plus the reasons for Unsorted, with card names (list capped; "and 6 more" expands).

**Singleton, 100-card, colour identity, proxies and finish.**
- **Singleton** is enforced by the ladder itself (rule 3 "duplicate"), never by blocking the import. Applies to singleton formats; for formats with a copy limit the limit replaces 1. [Confirmed: `src/lib/format-config.ts` `singleton`, `maxCopies`]. Cards that allow any number (for example Relentless Rats) are treated like any other duplicate in v1 and go to Unsorted; the owner can move them. [Approximate]
- **100-card warning.** Only **new slots** change the list size. If the main list (Maybeboard excluded, commanders included) ends above the format's target (100 for Commander, using `validateDeckCount`), the result says "Korvold now lists 103 cards, 3 more than 100". Filling empty slots never changes the size. Below target gives no warning. Warns, never blocks.
- **Commander colour identity.** Checked only for **new slots** (a card the deck already lists was already accepted by the owner). **Recommendation: warn, do not block**: the card is still added and the result names it ("Cultivate is outside Korvold's colours: B, R, G"). Reason: the owner chose this deck on purpose and a block would only send the card to Unsorted, which is just as visible and more annoying. Uses existing `decideCard`, `loadCardFacts`, `loadDeckFacts`. [Confirmed: `src/lib/chat-proposal-check.ts`]
- **Proxies.** An imported proxy fills or creates a slot like an original, marked proxy (D-026; the "use proxies" setting in D-059 decides whether it counts as owned, unchanged). The result counts how many proxies went into the deck.
- **Finish.** A new slot records the copy's finish and printing (D-038, D-041). A copy whose finish differs from what an existing slot asked for still fills it (as all existing assign paths do) but the result counts them: "2 foils filled non-foil slots". Exact printing and finish are preferred first (D-021).
- **Deck status.** The result shows the deck's readiness after the import (for example "Korvold is now Playable") using the existing deck status code, since filling the last empty slots can change it (D-002, D-059).

**Reuse of existing allocation and assignment code.**

- Planner: one pure function does the ladder above, in two forms kept in step by tests: in TypeScript for the forecast and unit tests (`planDeckImport`, in a small library file), and inside the database function for the write, where it reads the deck under a lock. **The database decision is the one that counts**; the forecast may differ if the deck changes in between, and the result screen always shows what happened. [Approximate: if two forms prove hard to keep in step, the forecast is cut, not the write.]
- Readers: nothing new. A placed copy is a normal `deck_cards` assignment.

**Atomicity and failure (single transaction).** New function `insert_user_copies_to_deck(p_user_id, p_rows, p_deck_id)` (service role only; function-only migration written by the Developer, **no table or column change**). In one transaction it: locks the deck row; inserts the copies through `insert_user_copies` (same call, same checks); then places each copy by the ladder; returns the insert result plus per-outcome counts and per-copy outcomes. 
- If any step raises, **the whole import rolls back: no copies, no slots, nothing** (same all-or-nothing as today's import). The screen says the import did not happen and nothing was added.
- A single copy that cannot be placed for a business reason (slot taken, identity mismatch) does **not** abort the import: that one placement runs in a sub-step, rolls back alone, and the copy stays in Unsorted with reason "could not place", counted in the result.
- A deck or box deleted between the owner picking it and the write: refused before any copy is written (`deck_not_found`, `storage_location_not_found`), nothing added, plain message "That deck/box no longer exists. Pick another place." The owner retries.
- The collection-card step (`user_cards` upsert) happens before the RPC today and is not part of the transaction [Confirmed: `manabox-collection-import.ts`]; it only adds card identity rows, is idempotent (upsert) and is unchanged.

**Idempotency and reconciliation.**
- The add-only collection import has **no duplicate-submit guard today** (each successful submit adds more copies; the dialog blocks a second click while saving) and no per-copy reconciliation: reconciliation (conflicts, claims, `finalize_import_claims`) belongs to **deck** imports and onboarding batches [Confirmed: `src/lib/import-reconciliation.ts`, `src/lib/import-sleeve-claims.ts`]. The destination does not change that and adds no storage, so no idempotency key is introduced. A failed attempt leaves nothing, so retry is always safe. A **repeat of the same import into the same deck** is safe in the sense that matters: the deck's slots are already filled, so every copy lands as a duplicate in Unsorted rather than a second fill. (If the owner wants true double-submit protection, that is a separate later item needing a stored import key.)
- Placed copies are ordinary filled slots, so the deck-import conflict screens and the onboarding reconciliation see them as already owned and assigned, never as conflicts. The import does not assign copies to slots in **other** decks and never pulls an existing copy out of another deck (D-047 unchanged). Two concurrent imports into one deck serialise on the deck lock; the second sees the slots the first filled.

**Effect on Deck health and spare counts.** [Confirmed: `src/lib/spare-copy-browse.ts`, `src/lib/deck-health-gap.ts`]
- A copy placed in a deck is in a slot, so it is **not spare** and the deck's gap list shrinks; a deck that was Unowned or Assembling because of those cards moves toward Playable at once. Copies sent to Unsorted or a binder are **spare** exactly like any other free copy (spare has no location test). New slots make the deck's list longer and show in its card count and 100-card check.
- After a deck destination, the app refreshes that deck's views (deck page, Deck health, Picklist, collection counts). No other deck is touched, so no other deck's numbers change. Owned counts rise by the number imported regardless of destination.
- Nothing here depends on Missing or In-hand, because import creates neither; once S0 lands, the same readers apply. The Picklist (4b): copies placed by import remove their rows from Available/Needs moving/Unowned for that deck.

**Safety.** No destructive operation: copies are only added; no existing copy, slot or location is changed or removed; no recompute. The only existing rows touched are the deck's empty slots (filled) and the deck's list (new slots added). Not undoable in one click in v1 (the add-only import has no undo today); the result screen lists exactly what went where so the owner can fix by hand. ## 6. Atomicity, concurrency, failure

- **Every tick is one RPC = one transaction.** Each RPC takes the same per-copy advisory lock the placement RPCs use, `pg_advisory_xact_lock(hashtextextended('collection-copy:' || copy_id, 0))` [Confirmed: `20260925220000_placement_source.sql`], then locks the item row and any slot row `FOR UPDATE`, checks the item state, and writes. If any step fails the whole tick rolls back: the item keeps its old state and the card stays where it was (for Placed: it stays In your hand). The screen shows the error and leaves the tick unticked.
- **Idempotent.** Found on a `found` item, Placed on a `placed` item and Cant-find on a `missing` item return success with the current state and change nothing (double taps, flaky phone connection).
- **Placed validation reuses the existing slot-identity trigger** (`trg_validate_deck_card_copy_identity`, [Confirmed: live trigger list]); a card that does not match the slot rolls back the tick.
- **`create_move_list`** inserts all rows in one transaction; the unique open-item index prevents two lists claiming one copy. Rows that cannot be created are returned in `skipped`, not silently dropped.
- **Slot ownership.** Placed into a slot someone filled in the meantime returns `slot_claimed_elsewhere`; the app offers another empty slot or a box. Nothing is overwritten.
- **Supply readers must change in the same slice that introduces the first writer.** A copy In your hand or Missing is not supply. Files that currently define "free copy" as "no deck row" and must add `NOT missing AND NOT in_hand` (single shared helper `isSupplyEligible` / `isSpare`, in the types file as reference): `src/lib/spare-copy-browse.ts`, `src/lib/owned-copy-lookup.ts`, `src/lib/allocation-candidates.ts` (two queries), `src/lib/card-status.ts`, `src/lib/supply-pool.ts`, `src/lib/reconcile-overuse.ts`, `src/lib/import-engine-v2.ts`, `src/lib/manabox-resolver.ts`, `src/app/api/collection/ownership-batch/route.ts`, `src/app/api/collection/allocation/route.ts`, `src/app/api/storage/overview/route.ts` (its "unsorted = no location and no deck" count would otherwise include in-hand and missing cards), `src/app/api/cards/locate/route.ts`. ## 7. Undo and safety

- **No destructive operation anywhere in this feature.** No delete, truncate, bulk clear, or "return everything". Items are never deleted (state `cancelled`/`placed`), copies are never deleted, and the only writes are to `in_hand`, `missing`, `missing_since`, `location_id`, `deck_cards.copy_id`/`ownership_status`/`placement_source` and `move_items`. Any future "put everything in hand back in Unsorted" or "clear Missing" is a separate action that needs owner approval.
- **Undo of the latest tick.** Found to to_find: copy goes back to its recorded slot (`from_deck_card_id`) if that slot is still empty, else to its recorded box, else stays in hand and the app says why (`slot_claimed_elsewhere`); it never takes a slot someone else filled. Placed to found: the slot or box is cleared and the copy is In your hand again. Missing to to_find: flag cleared, copy returns as for Found. Undo is one level (latest tick), because older ticks may already be built on.
- **Source recorded for audit.** Placements from the checklist write `placement_source = 'manual'` (owner clicked, D-009); the item row records `source` for how the list was made. AI never moves physical cards in this phase (D-034 would then require undo; out of scope).
- **System locations are protected.** `delete_storage_location` already refuses the default (Unsorted) [Confirmed: live function body]. Rename of Unsorted must be refused too (recommendation in section 11, Q4). In your hand and Missing are not rows, so they cannot be renamed or deleted at all.
- **Test account only.** All save-path tests run against the separate test account, never the owner's live data (process Gate 4). Until it exists, the Developer marks DB save-path tests "untested" instead of running them live.
