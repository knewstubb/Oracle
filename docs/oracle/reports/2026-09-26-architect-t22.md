## The three pending technical questions, answered

**1. Exact API field for per-instance alternate-printing selection.**

`import_sleeve_claims.selected_printing_id text NULL`. `NULL` means "use the
imported printing". `printing_id` is never overwritten, so the select's default
option is always recoverable. On the wire it is `ConflictInstance.selectedPrintingId`,
with `effectivePrintingId = selectedPrintingId ?? row.printingId` computed
server-side. Written via `PATCH /api/onboarding/reconciliation/instance/printing`.

**2. How persistence is stored so users can leave and return.**

Entirely server-side on `import_sleeve_claims`: `resolution`,
`selected_printing_id`, `wishlist`. No `localStorage`, no session state, no
client-derived supply maths. That is what makes "choices persist across tab
switches" true by construction rather than by client discipline — two tabs read
the same rows.

Resolved rows staying visible until reload falls out of two rules rather than any
client bookkeeping: `GET` defaults to `includeResolved=false`, and every mutation
returns the full view with `includeResolved=true`. The client replaces its list
from the mutation response, so a row it just resolved stays in place and goes
green; a full reload calls `GET` with the default and the row is gone.

**3. How counts are computed per conflict printing across tabs.**

A conflict printing is `(card_name, printing_id)`. It is `resolved` when no
instance is still `planned` and no `sleeved` instance is unsatisfiable. Every
badge counts unresolved conflict printings. Per-deck counts deliberately do not
sum to the tab badge: a printing wanted by three decks is 1 in the tab badge and
1 in each of three deck headers. All counts are computed in the read RPC, so the
UI never derives them.

## New decisions made (need owner confirmation)

1. **The conflict-printing key excludes finish.** The spec binds the printing
   identifier to `deck_cards.finish`, which does not exist — `deck_cards` has no
   finish column [Confirmed: `src/types/supabase.ts`], and the import pipeline
   persists no requested finish anywhere. The key is `(card_name, printing_id)`,
   matching `reconcile_built_deck`'s existing exact-printing rule. Finish is
   reported where it is real: the row header shows it only when every owned copy
   of the printing shares one finish, and alternate-printing options list the
   finishes actually owned.
2. **`resolution` values are renamed in the database**: `release` → `planned`,
   `sleeve` → `sleeved`. `release` no longer means release, and a permanent
   spec/UI/DB translation layer is how the `scryfall_id`-vs-`oracle_id` class of
   bug happens. Legacy strings stay accepted on input.
3. **Default state becomes `planned`.** This is what spec §8 and the design brief
   §4 ask for, and it is D-020 applied consistently. Consequence: the old summary
   screen shows no conflicts between this migration and the new UI. They must
   ship together. No data is lost.
4. **Slots that import already filled are not rows.** `reconcile_built_deck`
   assigns a copy whenever a free exact-printing copy exists, so those slots are
   already resolved. They still count as supply consumers and appear as
   `claimedBy` deck tags. The spec has no visual treatment for them; this is the
   Designer's call if the owner wants them visible.
5. **New routes rather than evolving `/api/onboarding/conflicts`.** The payload
   shape changes substantially; evolving in place would break the live screen
   between the contract commit and the UI commit. The old routes are retired in
   Phase 5.
6. **Wishlist is a column on the claim, not a new table.** The standalone
   wishlist list is explicitly deferred (spec §18); a table with no consumer is
   debt.
7. **Alternate-printing options omit `condition`.** Spec §12 asks for it, but
   selection is per printing while condition is per copy, so showing one copy's
   condition would be misleading when a printing has several. Copy-level
   selection is the natural next increment; it contradicts the locked
   per-printing grouping today.
8. **Finalization becomes per-instance.** The current all-or-nothing-per-card
   guard materialises nothing when a card is over-committed. With the UI and the
   RPC both preventing over-sleeving, that guard now only discards the user's
   good decisions for every other deck wanting the card.
9. **`get_deck_conflict_counts` is redefined** to "import slots this deck has not
   filled yet". The old supply-maths definition counted only `resolution =
   'sleeve'` and would report zero for every deck under the new default.
10. **Over-sleeving is rejected server-side** (`409 sleeve_supply_exhausted`).
    The UI already disables the button; the RPC re-checks because there is no
    tie-breaker to fall back on if a stale client writes.
11. **Changing an alternate printing demotes rather than rejects.** If the
    instance was `sleeved` and the new printing has no room, it drops to
    `planned` and the response carries `demoted: true`. Rejecting would trap the
    user; spec §12 says printing selection never blocks.

## In-scope correctness fixes found while designing

Three defects in the current `finalize_import_claims` that the redesign forces
into scope rather than around:

1. It assigns any free copy of the card name and retags
   `deck_cards.scryfall_id` to whatever it found — the printing drift T-21
   removed from `reconcile_built_deck` but left here. Violates D-021.
2. It always inserts a new proxy row instead of reusing a free one, so repeated
   runs accumulate duplicate proxies. Violates spec §8/§9.
3. It never clears `user_copies.location_id`, leaving an assigned copy
   simultaneously in a deck and in a storage location.
   `reconcile_built_deck` already does this correctly. This is a one-location
   integrity fix, in scope under the safety exception in
   `convention-personal-app-scope.md`.

It also never set `placement_source = 'import'`, required by
`docs/oracle/contracts/placement-source.md` row 12.

   deck-list conflict badge? The contract says yes.

Correction to the spec, for the UX/UI agent:

- Spec §19 binds the printing identifier to `deck_cards.finish`. That column does
  not exist. The row's finish comes from `user_copies.finish` and is only
  unambiguous when all owned copies of the printing share it.
- Spec §5 says a conflict printing maps to one row from `get_import_allocations`.
  It does not — that RPC groups by `card_name` and counts `owned` across all
  printings. The new `get_import_reconciliation` RPC provides the per-printing
  rows the spec describes.
