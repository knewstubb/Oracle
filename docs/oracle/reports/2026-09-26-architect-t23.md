## New decisions made (need owner confirmation)

- The **effective printing** for an instance lives on `import_sleeve_claims.printing_id`/`finish`, not on `deck_cards`. `deck_cards.scryfall_id`/`finish` remain the imported values until finalize writes the chosen printing back. This is less invasive than adding a separate override column and keeps the imported deck list stable during reconciliation.
- A **conflict printing** is keyed by `(scryfall_id, finish)`. This honors D-004 (finish is independent of printing) and D-021 (exact-printing matching). Counts, owned supply, and demand are all computed per printing+finish.
- `alreadyClaimedBy` lists only decks that currently have a **finalized** real copy of the printing assigned. It does not project which sleeve-intent claims would receive copies if finalized now, because the spec forbids a tie-breaker.
- `canSleeve` is computed by the backend: a non-sleeved instance can be switched to `Sleeved` only if the current number of sleeve-intent claims for that printing is strictly less than the owned supply.
- The read response keeps the existing top-level key `allocations` even though the row shape is new, to minimize churn in the RPC helper.

## Assumptions

- `deck_cards.finish` did not exist and is added by this migration. The UX spec's data-binding table referenced `deck_cards.finish`; adding it to the core table is necessary for finish-aware reconciliation.
- Imported Archidekt data does not include finish, so existing rows are backfilled to `nonfoil`. Future imports can populate `deck_cards.finish` when the source provides it.
- Basic lands remain excluded from `import_sleeve_claims` (existing behaviour), so the redesign does not change basic-land handling.
- Wishlist toggles remain local/separate persistence, as specified in the UX spec.
- The existing `/api/onboarding/conflicts/resolve` route will be updated by Backend to accept the new UI state values (`planned`/`sleeved`/`proxy`) in addition to the legacy DB values.

## Open questions

- Should the read RPC embed `alternatePrintingOptions` for every owned instance, or should the frontend fetch them lazily when the select is opened? The contract embeds them for simplicity; this can be revisited if performance becomes an issue.
- Should `alreadyClaimedBy` also include sleeve-intent claim decks when no finalized copies exist? The current contract lists finalized owners only.
