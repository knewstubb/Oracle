## What DB-5 does
- `deck_health_targets`: one row per deck and group (lands, ramp, card_advantage, interaction); `target` 0 to 100, `reason` (1 to 200 characters, required when Claude sets it), `set_by` (`claude` or `owner`), `previous` (the number replaced, for Undo), `batch_id`, `updated_at`; unique on (deck, group). `user_id` references `auth.users` (cascade), `deck_id` references `decks` (cascade). RLS: select own rows only; signed-in users have no write grant; every write is a service-role function. Same as DB-1 to DB-4.
- Claude writes through the existing `ai_submit_change('health_target', {deck_id, targets:[{group, target, reason}]})`. Applies at once, one batch, one log row per group, one Undo. A group with an owner row is skipped and returned as `left_alone`; a request naming only such groups is refused `target_overridden`. A repeat of the same number and reason is skipped as `unchanged`.
- Owner: `owner_set_health_target` (override, keeps the replaced number in `previous`), `owner_hand_back_health_target` (deletes the owner row), `get_deck_health_targets`. Owner Undo of a Claude batch goes through the existing `ai_undo_group` and leaves groups the owner has since overridden alone and says so.
- Not destructive. No existing row is changed. `deck_strategy.health_overrides` is not touched or read.

## New decisions made (need owner confirmation)
- Column is named `target_group`, not `group`, because `group` is a reserved word in SQL.
- Target range is 0 to 100 (the contract says "whole number" without a range).
- "Handed back to Claude" is stored as deleting the owner row, exactly as contract S17 and 3.6 say. The task text also mentions a "handed back" state; the contract wins, so no extra state column exists. If a visible "handed back" state is wanted (for example to keep the owner's old number on screen until Claude replaces it), that needs a contract change first.
- The contract's owner-side "Undo the last Claude change to a group (restore previous)" is covered by the existing batch Undo (which restores the earlier number and its reason from the log) rather than by a separate function, because `previous` holds only the number, not its reason.
- Claude's health requests go through the existing hourly and per-request gate like every other change. A request has at most 4 groups, so it is not held in normal use; if the hourly cap is reached it waits for approval like other kinds (the pending list accepts `health_target`).
